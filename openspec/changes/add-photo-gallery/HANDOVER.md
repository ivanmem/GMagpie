## 0. Правила работы (обязательны)

1. **Не трать токены на мелочи.** Правь только то, что влияет на работу: баги, гонок,
   утечек, падений, неверного результата. Опечатки в комментариях, вкус, переименования,
   «а можно было бы красивее» — НЕ трогай, если это не попутная одна строка в уже
   правимом месте. Рефакторинг — только там, где он снижает риск реальных дефектов
   (см. §5 P1/P2), а не ради красоты.
2. **Красный тест сначала.** На каждый фикс — тест, который НА НЕМ ПАДАЕТ до правки и
   зеленеет после. Поведенческие тесты (z-порядок, вспышки, соседство) — скриншотами/
   логами/окнами, не грепом исходника; греп-инварианты — только как страховка там, где
   поведение в тесте невоспроизводимо.
3. Язык комментариев/логов новых модулей — русский; строки UI — только `.resw`,
   4 локали (`language-ru`, `language-en-US`, `language-zh-Hans`, `language-zh-Hant`
   — у ru файла НЕ ЕСТЬ регион!). CJK-аудит добавленных строк держать на 0.
4. **Ничего не коммитить без явного запроса** пользователя (весь текущий объём лежит
   незакоммиченным намеренно). Исключение — фаза публикации (§7), там коммиты нужны.
5. Живые прогоны не должны мешать пользователю: убивать только процессы с
   `Path` вида `F:\Projects\cpp\Magpie\bin\*`; чужой GMagpie пользователя — не убивать
   без спроса; полноэкранные пробы — одним коротким заходом и с предупреждением.
6. После всех правок — полная батарея (§6) обязанна быть зелёной + `/code-review
   high --fix` прогнать самостоятельно и довести дерево до того же состояния.

## 1. Что за фича

Фотогалерея/слайдшоу поверх эффект-цепи масштабирования GMagpie Experimental
(C++20, WinUI3-остров, D3D11, DirectXMath, wil). CLI `GMagpie.exe --gallery <папка>
[--interval сек] [--mode "имя режима"]` открывает полноэкранный показ: ←/→/↑/↓,
колесо, Home/End, Space-пауза, F11/Esc — стоп, Num6 — окно выбора апскейлера
(включая нативный RTX Video VSR), Delete — файл в корзину, Compare в фото-сессии
выключен, на главной — карточка «Фотогалерея» с интервалом/выбором папки/«Продолжить»
+ прогресс «N / M» идущего показа. Постановка: `openspec/changes/add-photo-gallery/`
(proposal, design, tasks — 7.1..7.35, specs/photo-gallery/spec.md).

Ключевые файлы:
- `src/GMagpie/GalleryService.cpp/.h` — синглтон сервиса: плейлист, навигация, хуки,
  окно статуса, окно пикера (GDI, ownerless+WS_EX_TOPMOST+WM_TIMER 200мс страховщик
  z-порядка), удаление, прогресс-событие, лёгкий режим-зависимое поведение.
- `src/GMagpie.Core/PhotoFrameSource.cpp/.h` — источник кадров: ждёт запрос файла на
  своём потоке захвата + поток предзагрузки, декод WIC/WinRT (`RespectExifOrientation`).
- `src/GMagpie.Core/Renderer.cpp/.h` — фото-сессия: `_ResizePhotoEffects` (цепь под
  размер фото, лог «Геометрия фото-сессии»), `CalcPhotoEffectStages`,
  `_UpdateDestRect` (letterbox по аспекту фото), `_DrawPhotoSceneScaled`/
  `CalcPhotoSceneViewport` (прорисовка сцены в целевой прямоугольник через
  приватную копию `_photoSceneCopy` — SRV на scene-текстуру с keyed mutex нельзя).
- `src/GMagpie/ScalingService.cpp/.h` — запуск/остановка фото-сессии, `_photoStage`
  (окно-«приманка» источника на мониторе курсора), `RestartPhotoEffects`.
- `src/GMagpie/App.cpp/.h` — CLI парсер, `_galleryLiteMode` (см. §4.5), показ из
  командной строки.
- Тесты: `tests/prepare_photo_gallery_test.py` (извлекает чистые функции в
  `PhotoGalleryUnderTest.h`) → `tests/PhotoGalleryTests.cpp` (CPU, assert'ы);
  `tests/validate_photo_gallery_source.py` (+`--self-test`, 43 регрессии),
  `validate_photo_gallery_resources.py`, `validate_photo_gallery_state.py`,
  `Run-PhotoGalleryTests.ps1` (запуск CPU-тестов); живые зонды:
  `probe_photo_gallery_zorder.ps1` (z-порядок+screenshot), `probe_photo_gallery_flash.ps1`
  (вспышка пропорций), `probe_magpie_gallery_coexistence.ps1` (два экземпляра).

## 3. Что нельзя ломать (проверено живьём, дорогой ценой)

- **Z-порядок оверлеев**: статус и пикер — НЕ owned, `WS_EX_TOPMOST`, без LAYERED,
  непрозрачный фон, `WM_TIMER` 200 мс переставляет наверх полосы (`IsBelowOutputWindow`
  по цепочке `GW_HWNDPREV`). Любая попытка «навести порядок» — только с зелёным
  `probe_photo_gallery_zorder.ps1` + скриншотом. Инварианты `overlay-*` в self-test —
  это кладбище предыдущих заблуждений, не удаляй.
- **VSR (RTX Video)**: SDK 1.3.0.0 лежит в `F:\Projects\cpp\dependencies\
  NVIDIA-VFX-SDK-1.3.0.0-windows-x64`; сборка с `/p:EnableRTXVideoDenoise=true`.
  ABI строго 1.3 (0.7.6 — детект оффсетов/AV). Runtime DLL обязаны лежать рядом с
  exe (берутся из папки exe). Не «обновляй» SDK на main-ветку.
- **Цепь фото-сессии**: выход цепи всегда = размер кадра (нормализующий Fill-проход
  обязателен), вписывание делает фронтовый `_destRect` + `_DrawPhotoSceneScaled`
  (копия сцены в `_photoSceneCopy` ДО прорисовки — keyed-mutex текстуру в SRV нельзя).
  Смена размера фото — rebind цепи без рестарта сессии (`RequiresRebind`).
- **Compare (pass-through)** в фото-сессии отказан (`SetPassThroughActive`) и кнопка
  скрыта — фото-источник спит между страницами, история опорных кадров виснет.
- Одиночный экземпляр обычной модели поведения (SHOWME/QUIT, elevation-вытеснение) —
  не трогать для не-галерейных запусков.

## 4. Найденные ревью дефекты: ЧТО УЖЕ ИСПРАВЛЕНО (тесты есть)

Ниже — валидированные замечания (каждое проверено независимым агентом). Исправлено
автором, инварианты/тесты в batterry:

1. **Реентерабельность Delete (UB!)** — `SHFileOperationW` крутит модальный насос
   сообщений на UI-потоке, а LL-хуки галереи и авто-таймер живы: зажатая Delete
   (~31/с) или стрелка сдвигали `_index` под внешним `erase` → удаление не того
   файла или `erase(end())`. Фикс: флаг `_deleting` + `scope_exit`, пост-проверка
   `_running`, `erase` по `std::find(path)`, а не по индексу. Инвариант
   `delete-survives-message-pump`. НЕ проверено живьём (удержание Delete) — проверь.
2. **Протухшая причина отказа «Продолжить»** — `StartLast` возвращал false без
   обновления `_lastStartFailure` → тост с причиной ПРОШЛОГО запуска. Фикс: сброс в
   начале `StartLast`. Инвариант `start-last-resets-failure-reason`.
3. **EXIF-процент строки состояния** — `TryGetImageSize` читал WIC `GetSize`
   (размер закодированного потока), а на экран кадр идёт повёрнутым
   (`RespectExifOrientation`) → на Orientation 5..8 проценты перевёрнуты. Фикс:
   чтение `System.Photo.Orientation` + чистая `PhotoAppliesExifRotation` (CPU-тест).
   Живой проверки на реальном EXIF-файле не было.
4. **Лёгкий режим `--gallery`** (фича по запросу пользователя, не дефект): отдельная
   mutex-группа `...-Gallery`, без глобальных хоткеев/обновлений/STARTUP-уведомления/
   elevation-рестарта/автозапуска-админа, без foreground-таймера ScalingService, старт
   в трей. Инварианты `gallery-lite-*`, CPU-тест `HasGalleryArgument`, спека
   дополнена. Живой пробы соседства ещё не было (§2).

## 5. ПОДТВЕРЖДЁННЫЕ, НО НЕ ИСПРАВЛЕННЫЕ (порядок работ)

### P0 — влияет на работу у пользователя прямо сейчас

1. **Вспышка пропорций при перелистывании** (жалоба пользователя, открыта).
   Механика (гипотеза, подтверждена чтением кода): backend обновляет `_destRect`
   под новую фотографию (`Renderer.cpp ~4267`) ДО того как фронтьен заберёт новый
   кадр; любая перерисовка фронтьена со СТАРОЙ base-текстурой (курсор, оверлей,
   idle-present) берёт живой `_destRect` (`_CopySceneToTarget` ~1060/1083) и на
   ~100–500 мс (декод+перестройка цепи VSR) рисует старое фото в новых полосах.
   Фикс-направление: привязать геометрию к кадру — снапшотить `_destRect` во
   фронтенд-полях в момент adoption нового base-кадра (`~971`, там же где
   копируется `_frontendFrameMetadata`) и рисовать по снапшоту; снапшот обновлять
   также во фронтовых вызовах `_UpdateDestRect` (OnMove/OnEndResize/Initialize —
   это поток фронта). Красный тест УЖЕ ЕСТЬ: `tests/probe_photo_gallery_flash.ps1`
   (красный 16:9 → синий 1:1, покадровая классификация скриншотов; PASS = нет
   кадров «старое содержимое в новой геометрии»). Не выдумывай другой тест —
   доведи этот до зелёного.
2. **(P1, вердикт верификатора) Залипание `_photoSessionActive` / окна фото-сцены**:
   в обработчике `_ScalingRuntime_StateChanged` ранний `return` по `State() != value`
   (`ScalingService.cpp` 350) стоит ВЫШЕ teardown'а (`_photoStage.reset()` 369,
   `_photoSessionActive = false` 371) — устаревший Idle-ивент проглатывается.
   Названные в первичном замечании триггеры ОПРОВЕРГНУТЫ: `RestartPhotoEffects`
   Idle не порождает (состояние всё время Scaling; флаг и должен переживать
   пересборку), Smooth Motion перезапускает процесс (залипший флаг лишь ПОДАВЛЯЕТ
   легитимный перезапуск). Реальные условия: полный экземпляр + живущая фото-сессия +
   авто-масштабирование игры из `_CheckForegroundTimer_Tick` (force=true, состояние
   не проверяет): либо гонка дельты (50 мс тик в той же очереди), либо вообще без
   гонки — форс-старт ЗАМЕЩАЕТ фото-сессию Scaling→Starting→Scaling без Idle.
   Симптомы на время игры: хуки/оверлеи/`_running` галереи не сняты (повторный
   Start → «уже запущена»), пропущен Smooth Motion после игры; САМО излечивается
   следующим реальным Idle. В чистом `--gallery` экземпляре невозможно (нет
   foreground-таймера). Фикс-направление: teardown фото-сессии выполнять до/вне
   guard'а дельты (по самому факту прихода Idle-уведомления, а не по совпадению
   `State()`), плюс разбор `Invoke(false)` на Starting (`ScalingService.cpp:354/384`
   с guard'ом `IsPhotoSession()` в `GalleryService.cpp:567`). Поведенческий тест —
   фото-сессия + форс-старт игры: хуки сняты, `_running` сброшен.
3. **Гонка `_frameSource` только на NGX-fault пути**: штатная остановка backend
   заперта рукопожатием WM_QUIT→join и сериализована с dispatcher-лямбами —
   опровергнуто; но при сбое NGX (`Renderer.cpp ~4020-4034`) backend выходит без
   WM_QUIT и `cleanupBackend` делает `_frameSource.reset()` параллельно очереди
   фото-лябмд (TOCTOU `if (_frameSource)` → виртуальный вызов). Редко, но UAF.
   Минимальный фикс: на этом пути не ресетить `_frameSource` в scope_exit, а
   публиковать nullptr атомарно/сбрасывать на потоке фронта при `~Renderer`
   (разобраться, что дешевле и без риск). Добавь инвариант, что `_BackendThreadProc`
   не выходит с reset'ом `_frameSource` помимо join-пути.

### P1 — воспроизводимая рассинхронизация состояния (чинить после P0)

4. **Рассинхрон цикла апскейлеров при быстрых нажатиях** (подтверждено):
   `ScalingService::RestartPhotoEffects` (`~603-612`) пишет `_photoWorkingEffects`
   и делает `TryEnqueue`; лямбда `ScalingRuntime::RestartWithEffectParameters`
   (`~322-335`) молча отсеивается guard'ами (`_quitting`, `_commandGeneration`,
   `State()`, `RunId`, `hwnd`), когда перезапуск уже пересоздаёт окно (первая
   лямбда вызывает `Destroy()` → `++_runId` → все последующие в очереди — в мусор).
   Воспроизводится запятой стрелок в открытом пикере (дедуп `_num6Held` только на
   Num6, на стрелки — нет). Итог: `_cyclePos`/подсветка/тост впереди реальной цепи.
   Направление (неочевидное решение): сделать лямбду идемпотентной — исполнять
   ЗАПОСЛЕДНЕЕ запрошенное состояние (живое поле в ScalingService под мьютексом),
   а не захваченный снимок; либо гейтить enqueue пока предыдущий restart не
   применён, с логом. Обязателен тест (хотя бы инвариант «последняя заявка
   побеждает» + ручной прогон: быстро протыкать ↓ в пикере, сравнить подсветку с
   логом цепи).
5. **Исключение из блока таймера в `GalleryService::Start` (`~552-564`)**:
   `CreateTimer/Tick/Start` могут бросить `hresult_error` (путь из TryEnqueue-лямбды
   App просто глотает HRESULT) → фото-сессия и хуки остаются висеть до следующей
   попытки Start. Частотность ≈ нулевая, фикс копеечный: try/catch с `_Cleanup()`+
   `StopPhotoSession()` на отказе. Сделай вместе с P1-4 за одно касание файла.
6. **`_Cleanup`: `ProgressChanged.Invoke(0, 0)` вне try в noexcept-функции** —
   исключение из подписчика = `std::terminate`. Обернуть в try (подписчик —
   HomeViewModel, бросать не должен, но цена — строка).

### P2 — architecture-риски, решай по месту (не рефактори ради рефакторинга)

7. **Блокирующая работа в контексте WH_KEYBOARD_LL** (подтверждено как риск,
   частично это и причина P0-2/P1-4): в хук-проке исполняются `SHFileOperationW`
   (модальный насос), перезапуск цепи (`RestartPhotoEffects`→Destroy/Start!),
   WIC-чтение размера в статус-оверлее, возможный `SaveAsync` конфига. При
   превышении `LowLevelHooksTimeout` Windows молча выключает хук — галерея теряет
   управление. Минимальное лечение: вынести тяжёлое из стека хука в
   `Dispatcher().TryEnqueue` (пост-обработка), в хуке — только решение «наше/не
   наше» и отложенное исполнение. Осторожно: порядок клавиш/состояний (`_num6Held`,
   `_paused`, picker highlight) не сломать; z-страховщик не трогать.
8. **Два почти идентичных GDI-оверлея** (`gallery_status` ~100 строк и
   `gallery_picker`) — общий механизм (класс окна, TOPMOST+таймер страховщик,
   шрифт, меряние текста, Hide) дублирован; баги z-порядка чинились 5 раз
   одновременно в двух местах. Рефакторинг оправдан ТОЛЬКО с зелёной z-пробой;
   без неё не трогай.
9. **NGX-fault выход backend** (см. P0-3) — общий корень с §5.3; если решишь
   одним механизмом — хорошо.
10. **Прочее, не трогай без причины**: залипание ленивой инициализации
    `_DrawPhotoSceneScaled` при отказе одного из Create* (подтверждено, значимость
    теоретическая — OOM; почини попутно, если всё равно правишь функцию: общий
    `if (FAILED(...)) { сброс всех _photoBlit*; return; }`); одна зависшая запись
    SRV-кэша на ветке отказа `GetShaderResourceView` в `PhotoFrameSource` (P4,
    можно не чинить); Reflex-«залипание» — ОПРОВЕРГНУТО (есть парный
    `discardReflexRender` scope_exit, см. тест `ReflexCaptureCycleTests`);
    утечки GDI/хендлов/окон в галерее — независимый аудит утечек не нашёл
    (после повторных показов/остановок ничего не накапливается; `_photoSceneCopy`
    не течёт, SRV-кэш рендерера = одна запись).
